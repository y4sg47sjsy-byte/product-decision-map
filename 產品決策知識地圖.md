# 產品決策知識地圖

> 用途：與主管快速對齊「目前做到哪裡、為什麼要補基礎建設、下一步優先補什麼」。
>
> 核心目標不是建立龐大的數據制度，而是讓產品數據逐步具備：**可用 →
> 可判斷 → 可決策 → 可驗證**。

## 1. 全貌

``` text
Business Goal
    ↓
Opportunity / Leverage
    ↓
Problem Framing
    ↓
Measurement Design
    ↓
Data Foundation
    ↓
Observation / Analysis
    ↓
Insight
    ↓
Product Decision
    ↓
Align / Execute
    ↓
Outcome Validation
    ↓
Learning / Standardization
    ↺
```

## 3. 現階段優先級

### P0｜先讓資料「可用、可判斷」

1.  **Event Governance**
    -   盤點既有事件。
    -   淘汰無使用目的、重複或無法正確對應的事件。
    -   對齊設計、工程、營運的事件名稱、Trigger、Parameter 與用途。
2.  **Data Quality**
    -   核心事件上線前確認是否正確觸發。
    -   避免「有埋點」被誤認為「有可信資料」。
3.  **Baseline / Threshold**
    -   核心觀測指標建立歷史基準。
    -   區分正常波動、需調查異常、需立即處理異常。
    -   降低上線觀測依賴個人自由心證。

### P1｜讓資料「容易理解與診斷」

-   區分 Business Health / Feature / Release 三種觀測問題。
-   建立總流量的 Driver 拆解方式。
-   整理常見診斷路徑，降低每次異常都從零開始分析。
-   持續補足 Measurement / Analytics 的知識缺口。

### P2｜讓資料真正進入「決策與驗證」

-   增加 Data-driven Decision Case。
-   將 Insight 連結至 Design / Roadmap / Resource Decision。
-   建立 Outcome Validation 與 Learning Loop。

## 4. 與主管對齊的核心訊息

目前不是缺少「更多 Dashboard
或更多事件」，而是需要提高既有數據的**可用性與可判斷性**。

現階段優先補足事件治理、資料品質、Baseline
與判斷標準，是為了降低後續產品分析、上線觀測與跨部門溝通成本。待基礎穩定後，再逐步提高
Data → Insight → Decision → Outcome 的可重複性。

## 5. 長期方向（非本期績效承諾）

逐步形成可跨產品使用的 Product Decision 能力：

**Business Goal → Opportunity → Evidence → Decision → Execution →
Outcome → Learning**

新聞平台作為第一個高複雜度實戰場域；未來可再透過其他產品驗證哪些方法屬於跨產品通用能力。
